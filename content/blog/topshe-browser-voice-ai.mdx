## Start with a bounded experiment

The product question is whether a small local model can make an assistant useful without routing every conversation through a hosted language-model API. Topshe uses a quantised Qwen 2.5 model through wllama and WebAssembly, with a React interface and local conversation storage.

The name comes from Feluda’s assistant in Satyajit Ray’s stories. In product terms, the intended role is similarly modest: help with a question or a small planning task. It remains an experiment, not a promise that a small browser model can replace a complete connected assistant.

## Local inference has a first-use cost

The documented model download is approximately 900 MB. That makes first-use readiness a separate experience from later conversations. A progress state, recoverable downloads and an honest explanation of device requirements matter more than calling the product frictionless.

Running inference locally also moves constraints onto the user’s device. Available memory, browser behavior and competing activity can affect the experience. There is no published representative device benchmark establishing a universal response-time claim, so this case does not invent one.

## Separate the voice pipeline from the model

The project uses browser speech APIs for recognition and synthesis. A browser can process speech differently from how the language model processes text. In particular, speech recognition may involve a remote service. A locally running model is therefore insufficient evidence for a claim that no data leaves the device.

Wake-word support uses Picovoice Porcupine and requires its own access key. Push-to-talk is a fallback. These are product dependencies, not details to hide behind a broad offline label. The [MDN SpeechRecognition documentation](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition) explains the browser-support and remote-processing caveats.

## Delivered scope versus future ambition

The repository documents local conversation history with IndexedDB and an offline-capable application shell. It also describes calendar, email, news and smart-home integrations as planned. Those ideas should be read as a roadmap, not features a visitor can already rely on.

WebGPU is not an established completed acceleration path in the documented implementation. Likewise, a compatibility statement in a README is not a substitute for a tested device matrix. Text-only fallbacks and clear unavailable states are part of making the current scope understandable.

## The next useful evidence

Before positioning this as a dependable assistant, I would want first-use completion rates, model-load failures, memory use and response latency across representative devices. Speech should be evaluated separately, with its permissions and processing path made visible. Integration tests should follow actual connected workflows as they are built.

These are future validation needs, not results claimed from this project. The current artifact demonstrates browser-local inference and the interface around it. The lesson is to make a narrow privacy claim accurately, and to treat dependencies and unsupported capabilities as part of the user experience.

See the [Topshe implementation and roadmap](https://github.com/saswatasg/topshe) for the documented architecture and current scope.
