## Start with the reason for the message

Renewals, transaction states, compliance errors and feature announcements serve different needs. A useful trigger inventory explains what changed, who needs to know and what action they can take. This makes it possible to distinguish an urgent operational message from a discretionary reminder before writing the copy. A catalogue of messages without this distinction is a list, not an architecture.

## Resolve conflicts before sending

Priority only helps if the system has a rule for competing messages. The design uses P0–P3 tiers and a daily cap to make that decision explicit. The operational specification also needs to explain suppression, expiry and exceptions: a message can lose relevance while waiting in a queue. The public case documents the approach, but does not provide a complete production implementation that a reader should assume is reproduced here.

## Make the message relevant to the context

The regional calendar brings occasion-specific context into the same architecture as renewals and transactional messages. A calendar should support relevance rather than create an obligation to contact every user on every date. Plan eligibility and geographic context need to be applied before delivery. The greeting integration is a related feature, whose reported engagement result should remain distinct from the notification system itself.

## A measurement plan for the whole channel

A sensible evaluation would track eligible users, suppression reasons, delivery, the intended action and disengagement. Opens alone do not show usefulness, and a declining complaint count can be misleading if delivery also fell. Comparisons need a defined cohort and period. These are recommended measurement questions, not results reported from this project.

## The useful takeaway

The product contribution is to make messaging decisions consistent and understandable across teams. Trigger inventory, priority, conflict rules and contextual eligibility belong in the same specification. Read the [notification case](/case-studies/livekeeping-notifications) and the [Send Greetings story](/blog/ai-send-greetings-168). The [Firebase messaging documentation](https://firebase.google.com/docs/cloud-messaging) provides delivery-platform context; it does not establish this project’s outcomes.
